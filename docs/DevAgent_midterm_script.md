## Slide 3: 项目背景与目标（1.5-2分钟）

### 行业痛点

做这个项目的出发点其实很朴素——**传统的软件开发流程太繁琐了**。从需求分析、架构设计、代码编写、测试，到修复Bug，每个环节都需要大量人工参与。开发者把大量时间花在重复性工作上，比如写脚手架代码、写测试、写文档。

现在市面上有很多 AI 编程助手，比如 GitHub Copilot，但它们**只提供代码补全**，缺乏端到端的自动化能力——没有需求分析、没有架构设计、没有测试生成、没有Bug修复。

另外还有一个关键问题——**缺乏有效的人机协同机制**。AI 生成的代码，人怎么审？怎么控？如果不能让开发者参与到AI的工作流程中，产出的质量就难以保证。

最后，LLM 生成的代码存在**幻觉问题**——可能生成不存在的API、逻辑错误的代码等。

### 项目目标

针对这些问题，我们设定了明确的目标：

**第一**，构建一个统一平台，用 LLM 驱动多个专业 Agent 协同工作。

**第二**，实现从需求到交付的**全流程自动化**——不是只做代码补全，而是覆盖整个软件工程生命周期。

**第三**，提供**实时人机交互审核**机制——AI 做完每个阶段，人审、人批、人改，保证产出质量可控。

**第四**，设计**双模执行引擎**——结构化流水线保证稳定性，自主探索模式应对灵活场景。

**第五**，提供**30种工具 + 8个专业Agent**，覆盖软件工程全流程。

目前项目规模：62个源文件、超过2.3万行代码、286个测试用例全部通过。下方这五个数字可以让大家对项目体量有一个直观感受。

## Slide 4: 系统总体架构（2分钟）

这是我们系统的总体架构图，采用了**六层分层设计**，从下到上依次是：

### 入口层（最上层）

用户可以通过三种方式与 DevAgent 交互：**CLI 命令行**、**REST API**（适用于程序调用）、以及 **VSCode/IntelliJ/Eclipse 等 IDE 扩展**。

### 路由层

根据用户指定的 `--mode` 参数进行**模式路由**。比如 `--mode full` 走流水线模式，`--mode agentic` 走自主探索模式。这一层的设计使得系统可以在不同场景下选择最合适的执行策略。

### 执行引擎层（核心）

这是我们系统的**心脏**。包含两个执行引擎：
- **PipelineRunner**：Plan-Execute-Gate 模式，代码硬编码阶段序列
- **DevAgentCore**：ReAct 自主模式，LLM 自主决策

### 工具层

30种工具，分为四大类：Pipeline工具、代码操作工具、GitHub集成工具、交互审核工具。

### 交互控制层

负责**人机协同**。包括跨线程通信（ThreadChannel）、多客户端管理（SessionManager）、阶段审核（PhaseReviewGate）、交互控制（InteractionController）。

### 增强模块层

提供**质量保障**能力。包括四层上下文管理、三层混合故障定位、中央产物仓库、沙箱执行环境等。

整个架构的数据流是**自上而下**的：用户请求 → 模式路由 → 执行引擎 → 调用工具 → 交互审核 → 生成产物。

## Slide 5: 双模执行引擎（1.5分钟）

这是 DevAgent 最核心的设计决策——**双模执行引擎**。为什么要双模？因为不同的任务场景需要不同的执行策略。

### Plan-Execute-Gate 模式（左侧）

适用于**结构化任务**，比如 `--mode full`（全流程开发）、`--mode design`（仅设计）、`--mode implement`（实现+测试）。

这个模式的核心思想是：**代码决定流程，LLM 只负责内容生成**。整个流程分为 5 个阶段：

1. **需求分析**：调用 analyze_requirements 工具，LLM 生成需求规格文档
2. **架构设计**：调用 design_architecture，生成 C4 架构图 + Mermaid 图表
3. **代码生成**：调用 generate_code，生成工程级 Python 项目
4. **测试执行**：生成 pytest 测试套件并执行，所有测试必须通过
5. **最终交付**：生成执行报告和质量仪表盘

每个阶段完成后都有三个步骤：**确定性验证 → 人工审核 → approve/revise/reject**。如果 revise，最多回退 2 次，超限自动推进。

### ReAct 自主模式（右侧）

适用于**探索性任务**，比如 `--mode agentic`（自主模式）、`--mode repair`（Bug修复）、`--mode debug`（调试分析）。

这个模式遵循经典的 **Think → Act → Observe** 循环。LLM 自主决策每一步操作。循环内嵌了**5个交互检查点**：
- CP1: 处理用户实时指令
- CP2: 暂停/恢复
- CP3: 终止条件检测
- CP4: 危险操作审批门
- CP5: 进度发布

还有一个关键机制叫**强制工具注入**：当人工审核做出决策后，系统跳过 LLM 推理，直接执行指定的工具，确保审核结果100%被执行。

两种模式通过路由层无缝切换，共享同一套工具和交互机制。

## Slide 6: 30种专业工具体系（1分钟）

我们的工具体系分为三大类：

### Pipeline 工具（8种）

从 plan_task 任务分解，到 analyze_requirements 需求分析、design_architecture 架构设计、generate_code 代码生成、generate_tests 测试生成、debug_issue 调试分析、repair_code Bug修复，最后 generate_report 生成报告。覆盖了软件工程的完整生命周期。

### 代码操作工具（14种）

包括文件操作（read/edit/write/list）、代码搜索（grep_text/ast、find_symbol）、命令执行（shell_run/test_run/lint_check）、版本控制（git_diff/log/blame）、信息获取（web_search/read_docs）。

### GitHub + 交互审核工具（8种）

GitHub 集成方面支持 Issue 读取和 PR 管理。交互方面有三个核心工具：
- **ask_user**：Agent 主动向人提问
- **request_review**：阶段成果提交人工审核
- **submit**：任务完成提交

所有工具都基于 **BaseTool 抽象类**实现，自动生成 JSON Schema 供 LLM 的 Function Calling 使用。

## Slide 7: 实时交互审核系统（1.5分钟）

这是 DevAgent **最关键的创新之一**——因为在 AI 辅助软件工程中，**人机协同不是可选项，而是必选项**。

### 完整交互链路

整个审核链路分 6 步：

1. Agent 完成阶段工作后，调用 request_review 工具
2. 系统自动进行**文件存在性验证**——确保 Agent 真的生成了文件，而不是空口说白话
3. **顺序锁检查**——已经批准过的阶段不能重复审核，防止绕过去
4. **速率限制**——全局计数器 ≥ 3 次后强制提交，防止审核死循环
5. 通过 **ThreadChannel** 跨线程通信，将审核请求推送到客户端
6. 人工通过 WebSocket 弹窗 / CLI 终端 / REST API 做出决策

### 通道回退策略

这里有一个很实用的多级回退机制：
- **最优先**：WebSocket 实时双向通信，VSCode 右下角弹窗
- **备选**：CLI 终端交互，命令行输入决策
- **备选**：REST API 轮询
- **兜底**：15秒超时自动批准，保证流程不会卡死

### 六种稳定性保障

为了保证交互审核的稳定可靠，我们设计了六种机制：顺序锁防止重复审核、速率限制防止死循环、修订上限（最多2次revise）、强制工具注入（审核决策100%执行）、文件验证（必须有真实产出）、分级超时（不同阶段不同超时时间）。

## Slide 8: 核心技术亮点（1.5分钟）

我想重点介绍四个技术创新：

### 1. 四层上下文管理 + 缓存优化

我们设计了四层上下文架构：
- **SYSTEM 层**：完全静态，可以跨轮次缓存，减少延迟和成本约50%
- **REPO MAP 层**：半静态，基于文件修改时间增量更新
- **DYNAMIC 层**：每轮变化，根据执行阶段动态分配token预算
- **幻觉防护层**：所有代码引用包含 file:line 锚点，测试失败原文展示不摘要

### 2. 三层混合故障定位

这是 Bug 修复的核心能力，融合了三种技术：
- **SBFL**（频谱故障定位）：运行时采集执行轨迹 + Ochiai 公式计算可疑度
- **Static**（静态分析）：AST 模式匹配检测常见缺陷
- **LLM Fusion**：融合前两层结果，输出精确位置和置信度

这个设计参考了 NUS AutoCodeRover 的 SBFL+LLM 混合策略。

### 3. 中央产物仓库 + 质量门

所有 Agent 产物统一注册到 ArtifactRegistry，包含 SHA256 校验和、文件大小、MIME 类型等元数据。采用原子索引写入防止并发损坏。

### 4. BaseAgent 自反射机制

每个 Agent 在输出后会进行**五维质量自审**（完整性、正确性、一致性、具体性、可操作性），不合格自动重做，最多2轮迭代改进。

## 附录: 可能的问题 & 准备回答

### Q1: 和 GitHub Copilot / Claude Code 有什么区别？

A: Copilot 是代码补全工具，Claude Code 是对话式编程助手。DevAgent 的差异化在于：
1. **端到端全流程**：不只是写代码，而是从需求分析到测试交付
2. **人工审核机制**：每个阶段强制人工审核，不是黑盒输出
3. **多 Agent 协同**：8个专业 Agent 各司其职
4. **双模引擎**：既支持结构化流水线（稳定可控），也支持自主探索（灵活应对）

### Q2: 为什么选择 DeepSeek 作为默认模型？

A: 两个原因：一是成本优势，DeepSeek API 的价格远低于 GPT-4；二是中文能力，DeepSeek 的中文理解和生成质量在评测中表现优异。系统同时支持 OpenAI，可通过 `--provider openai` 切换。

### Q3: 人工审核会不会太慢？影响效率？

A: 我们设计了三层保障：1）非交互模式下自动批准；2）分级超时机制；3）修订上限。在完全自动模式下，60-90秒即可完成全流程。交互模式让人在关键节点介入，反而避免了后期大规模返工。

### Q4: 代码生成的质量如何保证？

A: 四层保障：1）确定性验证（syntax + lint + import + pytest 全部通过）；2）LLM 10维质量评估；3）人工阶段审核；4）BaseAgent 自反射改进。多重机制叠加确保产出质量。

### Q5: 目前支持哪些编程语言？

A: 当前主要支持 Python。中短期计划扩展到 TypeScript、Go、Java。工具层的设计是语言无关的，扩展新语言主要是增加对应的模板和验证规则。

### Q6: 如何处理 LLM 幻觉问题？

A: 我们的四层上下文管理专门设计了幻觉防护层：所有代码引用包含 file:line 锚点、测试失败原文展示不做摘要、阶段自适应工具范围缩小、Read-before-edit 强制要求。加上确定性验证体系（syntax/lint/test），即使 LLM 产生幻觉，也会在验证阶段被拦截。

### Q7: 30种工具是否太多了？Agent 能正确选择吗？

A: 实际上工具多反而降低了选错的概率。因为每个工具职责单一明确，LLM 更容易做出正确选择。此外我们还有 ContextualToolFilter——根据执行阶段动态过滤可用工具，缩小决策空间。
