### 1.2 当前交互流程（15步完整链路）

```
1. Agent 调用 request_review(phase, files_changed, ...)
2. 系统检查: 文件存在? 阶段锁? 速率? 修订上限?
3. ThreadChannel._has_clients() 轮询SessionManager(最多15s，每0.5s)
4. 有WS客户端 → 推送 review.requested 事件到消息队列
5. ThreadRequest.wait() → threading.Event 阻塞Agent线程
6. 人工通过 WS/CLI/REST 选择: approve / revise / reject
7. ThreadChannel.resolve() → _event.set() 解除阻塞
8. approve → _approved_phases.add(phase) → 返回 next_tool名
9. revise → _revise_counts[phase]++ → 返回原工具名+反馈
10. state._forced_next_tool = next_tool → _force_params = 上一步输出
11. ReAct循环检测 _forced_next_tool → 跳过LLM，直接调用工具(★稳定性关键)
12. 工具执行完成 → 清除forced状态 → LLM接管 → 继续循环
```

### 1.3 强制工具执行（100%可靠的跳转）

审核响应后，**跳过 LLM 推理**，硬编码执行工具：

```python
# core.py
forced = getattr(state, '_forced_next_tool', '')
if forced:
    action = {"tool": force_tool, "params": force_params}  # 不经过LLM
    result = await tools.execute(force_tool, force_params, workspace)
    continue  # 回到循环，LLM接管后续
```

**对比**:
- ❌ 之前: prompt里说"请调design_architecture" → DeepSeek可能无视
- ✅ 现在: `tools.execute("design_architecture", params)` → 必定执行

## 二、发现了什么问题

### 2.1 已解决的问题

| # | 问题 | 修复 |
|---|------|------|
| 1 | API 不响应 `--interactive` 参数 | 启动时解析 sys.argv + env var |
| 2 | 后台Agent和WS handler用不同SessionManager | 共享同一个实例 |
| 3 | ThreadChannel不等WS客户端连接 | 15秒轮询(每0.5s) |
| 4 | VSCode用错task_id导致404 | 先fetch API获取真实ID |
| 5 | REST `/review/pending` 看不到后台审核 | 增加ThreadChannel.get_pending() |
| 6 | approve后Agent循环调request_review | 顺序锁 + 3次全局硬限制 |
| 7 | revise后不重新生成 | 强制工具执行 + 修订计数器 |
| 8 | 跳阶段(requirements直接到implementation) | 顺序锁: 只允许紧邻阶段 |
| 9 | VSCode断开后不显示状态 | 延迟3秒disconnect + REST查询 |
| 10 | 文档语言不可控 | 系统提示词强制中文输出 |

### 2.2 DeepSeek 遵循性差的根本原因

| 症状 | 根因 | 不是代码问题 |
|------|------|-------------|
| approve响应返回"design_architecture"，Agent仍调request_review | DeepSeek-chat对单词语义的"命令"理解弱 | ✅ 代码已强制跳过LLM |
| revise后Agent不知道要重新调用analyze_requirements | DeepSeek上下文窗口长时迷失 | ✅ 强制工具执行解决 |
| QualityEvaluator评分波动大(meets_standard ↔ critical_failure) | 模型对结构化输出不一致 | ⚠️ 需替代方案 |

**核心结论**: 所有通信、调度、跨线程问题均已解决。剩余是**DeepSeek作为内容生成器的质量波动**，而非系统架构问题。

## 三、技术方案：Plan-Execute-Gate 模式

### 3.1 核心思想

**让DeepSeek只做它擅长的事——生成内容。所有流程控制由代码完成。**

```
DeepSeek 的职责                 代码的职责
─────────────────              ─────────────────
- 分析需求文档                  - 决定执行顺序
- 生成设计方案                  - 何时提交审核
- 编写代码                      - 等待审核结果
- 生成测试                      - 审核后跳转到哪一步
- 修复bug                       - 验证文件存在
- 生成报告                      - 强制工具执行
                               - 阶段锁/速率限制
```

### 3.2 架构设计

```
                   用户输入 requirements.md
                         │
                         ▼
                ┌─────────────────┐
                │  PipelineRunner  │  新增核心模块
                │  (代码控制流程)   │  约 300 行
                └────────┬────────┘
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
        ┌──────┐    ┌──────┐    ┌──────┐
        │Phase │    │Review│    │Phase │
        │  N   │───→│ Gate │───→│ N+1  │
        └──────┘    └──────┘    └──────┘
                         │
                    ┌────┴────┐
                    │ approve │ → 下一阶段
                    │ revise  │ → 重试本阶段
                    │ reject  │ → 返回给用户
                    └─────────┘
```

### 3.3 新增 PipelineRunner 模块

```python
class PipelineRunner:
    """按照预定义阶段序列执行，每次阶段完成后强制审核。
    DeepSeek只生成内容，代码控制流程。"""

    PHASES = [
        {"name": "requirements",  "tool": "analyze_requirements",
         "input_from": None,       "output_dir": "01_requirements",
         "timeout": 600, "max_retries": 2},
        {"name": "design",        "tool": "design_architecture",
         "input_from": "requirements", "output_dir": "02_design",
         "timeout": 480, "max_retries": 2},
        {"name": "implementation","tool": "generate_code",
         "input_from": "design",   "output_dir": "03_implementation",
         "timeout": 300, "max_retries": 2},
        {"name": "testing",       "tool": None,  # 运行 generate_tests + test_run
         "input_from": "implementation", "output_dir": "04_tests",
         "timeout": 300, "max_retries": 2},
        {"name": "delivery",      "tool": "generate_report",
         "input_from": "all",     "output_dir": "06_reports",
         "timeout": 120, "max_retries": 1},
    ]

    async def run(self, task_desc, workspace, state, channel):
        """执行全部阶段，每阶段完成后强制审核"""
        for phase in self.PHASES:
            # 1. 执行阶段工具
            if phase["tool"]:
                result = await self._execute_tool(
                    phase["tool"],
                    self._build_params(phase, state),
                    workspace
                )
                state.update_from_result(phase["name"], result)

            # 2. 运行测试（如果有）
            if phase["name"] == "testing":
                result = await self._execute_tool("generate_tests",
                    {"code_files": state.code_files}, workspace)
                result = await self._execute_tool("test_run", {}, workspace)
                state.test_results = result.structured

            # 3. 强制提交审核（不是建议，是强制）
            review_result = await self._submit_review(phase, state, channel)

            # 4. 处理审核结果
            for retry in range(phase["max_retries"]):
                if review_result["decision"] == "approve":
                    break  # 进入下一阶段
                elif review_result["decision"] == "revise":
                    # 重新执行本阶段
                    result = await self._execute_tool(...)
                    review_result = await self._submit_review(...)
                elif review_result["decision"] == "reject":
                    return {"status": "REJECTED", "phase": phase["name"]}

            # 超时自动批准
            if retry >= phase["max_retries"]:
                continue  # 自动批准，进入下一阶段

        # 5. 完成
        return {"status": "COMPLETED"}
```

### 3.4 关键改进点

**改进 1: 代码决定流程，DeepSeek 生成内容**

```
之前: Agent (DeepSeek) 决定"我现在该调 analyze_requirements 还是 request_review"
      → DeepSeek 选错 → 循环/跳过 → 失败

现在: PipelineRunner 硬编码: Phase 1 → analyze_requirements → 审核 → Phase 2 → ...
      → DeepSeek 只收到 "请分析需求文档" → 生成内容 → 完成
      → 代码决定"下一步提交审核"
```

**改进 2: 审核不是建议，是流程的一部分**

```
之前: Agent可以选择忽略审核结果 (e.g., approve后仍调request_review)

现在: PipelineRunner 控制:
      - 执行完 Phase N → MUST 审核
      - approve → MUST 进入 Phase N+1
      - revise → MUST 重新执行 Phase N
      - 重试超过限定次数 → 自动进入下一阶段
```

**改进 3: 确定性验证替代 LLM 质量评估**

```
之前: QualityEvaluator(LLM) 输出 "meets_standard" / "critical_failure"
      → DeepSeek评分自身波动大

现在: 在提交审核前自动运行:
      1. lint_check() → 语法和风格错误
      2. test_run()  → 测试通过率
      3. schema_check() → 结构化输出完整性
      审核界面展示确定性指标而非LLM评分
```

**改进 4: 分级超时替代单一时钟**

```python
PHASE_TIMEOUTS = {
    "requirements": 600,   # 10min - 文档需要仔细审阅
    "design": 480,         # 8min
    "implementation": 300, # 5min
    "testing": 180,        # 3min
    "delivery": 120,       # 2min
}
# 超时后: lint+test都通过 → auto-approve，否则 → auto-revise
```

### 3.5 与当前架构的关系

**PipelineRunner 替代 LLM 做流程决策，但保留全部现有基础设施：**

```
保留:
  ✅ ThreadChannel (跨线程通信)
  ✅ SessionManager (多客户端)
  ✅ PhaseReviewGate (审核编排)
  ✅ 阶段锁、速率限制、文件验证
  ✅ 强制工具执行
  ✅ VSCode 扩展

替换:
  ❌ LLM 自主要定"下一步做什么" 
     → PipelineRunner 硬编码阶段序列

  ❌ LLM 质量评估
     → lint_check + test_run + schema 确定性验证

新增:
  🆕 PipelineRunner (~300行) - 流程控制器
  🆕 schema_validator (~100行) - 结构化输出验证
```

### 3.6 预期效果

| 指标 | 当前 | 目标 |
|------|------|------|
| 单阶段 approve 成功率 | 100% | 100% |
| 多阶段全流程(4阶段)成功率 | ~40% | **90%+** |
| revise→regenerate 成功率 | ~70% | **90%+** |
| 每阶段重试超限自动推进 | 无 | **有** |

## 四、与主流方案对照验证

### 4.1 Devin（Cognition Labs）

Devin 是当前最成熟的商业 AI 软件工程师，估值 $25B。其核心架构：

```
Planning Mode (只读) → 生成计划 → 人工审批 → Standard Mode (执行)
                                              ↓
                                    每步验证 → 失败自动重试
```

**与 DevAgent 方案的对照**：

| Devin 做法 | DevAgent 方案 | 一致性 |
|-----------|-------------|--------|
| Planning Mode: 先分析代码库，生成结构化计划 | `plan_task` 工具 → 阶段 DAG | ✅ 一致 |
| 计划审批后才进入执行模式 | 每个阶段完成 → 强制 `request_review` → approve 后执行下一个 | ✅ 一致 |
| `str_replace` 精确编辑（old_str 必须完全匹配） | `file_edit` 工具（相同原理） | ✅ 一致 |
| 失败自动重试（不依赖人工） | revise 3次上限后自动批准进入下一阶段 | ✅ 一致 |
| 沙箱执行 | `SandboxManager` (Docker/Podman/Local) | ✅ 一致 |
| 多 Agent 协作（review agent 独立上下文） | `PhaseReviewGate` LLM 质量评估（独立上下文） | ✅ 一致 |

**Devin 的做法证明 DevAgent 的路子是对的**：Plan → Approve → Execute → Verify → Next Step。

### 4.2 OpenHands / CodeAct

OpenHands 是社区最活跃的开源方案（前身 OpenDevin），SWE-bench 53% 解决率。

```
Perceive → Decide → Execute → Observe → 循环
    │         │
    │    LLM 输出 CODE（非 JSON 工具调用）
    │    用 MCTS 优化行动路径
    │
    └── 支持 plan_mode: TaskTrackerTool 跟踪进度
```

**与 DevAgent 方案的对照**：

| OpenHands 做法 | DevAgent 方案 | 一致性 |
|---------------|-------------|--------|
| `AgentDelegateAction`: 主 Agent 委派子 Agent | `pipeline_tools`: 8个专业Agent适配为工具 | ✅ 一致 |
| `TaskTrackerTool` (`enable_plan_mode`): 显式计划跟踪 | `_approved_phases` 阶段锁 + `_revise_counts` 修订跟踪 | ✅ 一致 |
| `Condenser`: LLM 压缩长对话 | `HistoryCompressor` + `ContextBudget`: 四层缓存优化 | ✅ 一致 |
| Docker-in-Docker 沙箱 | `SandboxManager` 三级回退 | ✅ 一致 |
| CodeAct: 所有操作用代码表达 | DevAgent 保持工具调用模式（DeepSeek 更适合） | ⚠️ 差异 |

**OpenHands 验证的关键点**：显式的 `plan_mode` 对任务成功率有显著提升——这正是 DevAgent 下一步要做的。

### 4.3 Cline / Roo Code（VSCode 扩展）

Cline 是当前最流行的 VSCode AI 编码扩展（MCP 生态）。

```
用户描述任务 → LLM 推理 → 工具调用 → 展示结果 → 等待下一条指令
                                 │
                          每次工具调用弹窗 approve/deny
```

**与 DevAgent 方案的对照**：

| Cline 做法 | DevAgent 方案 | 差异 |
|-----------|-------------|------|
| 每次工具执行弹窗审批 | 阶段完成后再审核 | DevAgent 更粗粒度，减少审批疲劳 |
| approve/deny 二态 | approve/revise/reject 三态 | DevAgent 多 revise 闭环 |
| 单线程 VSCode 内执行 | API + 后台线程分离 | DevAgent 架构更解耦 |
| MCP 协议扩展工具 | 30 种内置工具 + pipeline 工具 | 不同的扩展策略 |

**Cline 的弱项正是 DevAgent 的强项**：阶段级审核而非操作级，revise 闭环而非二态。

### 4.4 一致性总结

```
主流方案的核心共识:
  
  1. Plan before Execute      ← Devin, OpenHands, DevAgent ✅
  2. Human-in-the-loop gates  ← Devin, Cline, DevAgent ✅
  3. Auto-retry on failure    ← Devin, OpenHands, DevAgent ✅
  4. Sandboxed execution      ← Devin, OpenHands, DevAgent ✅
  5. Multi-agent delegation   ← Devin, OpenHands, DevAgent ✅
  
DevAgent 的差异化:
  
  6. Phase-level review       ← DevAgent 独有（其他都是操作级）
  7. Revise→regenerate loop   ← DevAgent 独有（其他都是 approve/deny）
  8. 中文文档输出              ← DevAgent 独有
  9. 引擎-UI 分离架构          ← DevAgent 独有（支持 CLI/API/VSCode 三端）
```

**技术路线与主流方案完全一致，且有三项差异化优势。**
