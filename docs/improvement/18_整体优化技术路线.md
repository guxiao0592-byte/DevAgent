# DevAgent 成熟 Agent 智能体技术改造方案

## 1. 文档目标

本文档用于总结 DevAgent 当前项目结构、已有技术能力、主要短板，以及后续将其升级为成熟 Agent 智能体平台的技术改造方案。

本方案重点解决以下问题：

1. 提升 Agent 输出稳定性。
2. 提升图表渲染质量与可复现性。
3. 提升 Web 前端交互体验。
4. 建立任务状态、审核、事件、产物的持久化机制。
5. 建立端到端质量验证和回归评测体系。
6. 将当前项目从高级原型升级为可长期迭代、可交付、可审计的成熟 Agent 平台。

---

## 2. 当前项目总体判断

DevAgent 当前已经具备较完整的软件工程智能体基础，核心能力包括：

1. 支持 CLI、Web 前端、VSCode 插件多入口。
2. 后端统一使用 DevAgentCore 作为核心执行引擎。
3. 支持 ReAct 自主循环和 Plan-Execute-Gate 确定性流水线双模式。
4. 具备需求分析、架构设计、代码生成、测试生成、调试修复、报告交付等完整流程。
5. 已有工具系统、上下文管理、阶段审核、故障定位、沙箱执行、多 Agent、多模态、可观测性等模块。
6. 前端已经接入任务创建、阶段进度、文档查看、图表展示、审核交互、报告下载等能力。

但从成熟产品角度看，目前仍存在以下关键短板：

1. LLM 输出解析不够稳定。
2. Pipeline 阶段产物契约不够严格。
3. 图表渲染依赖前端 Mermaid 和外部 Kroki，正式产物一致性不足。
4. 审核、事件、任务状态缺少生产级持久化。
5. 前端缺少完整状态机和工程化架构。
6. Agent 执行过程缺少可审计账本。
7. 缺少完整 E2E 回归测试和 LLM 输出质量评测体系。

---

## 3. 改造总目标

本次技术改造的总目标是：

将 DevAgent 从“功能完整的 Agent 原型平台”升级为“稳定、可恢复、可审计、可验证、可交付的成熟 Agent 智能体平台”。

具体目标如下：

| 目标方向  | 说明                                    |
| ----- | ------------------------------------- |
| 输出稳定  | 所有 Agent 输出必须经过结构化协议、Schema 校验和产物契约验证 |
| 图表稳定  | 图表必须支持服务端渲染、缓存、自动修复、SVG/PNG 导出        |
| 交互高质量 | 前端需要支持任务状态机、实时事件、审核卡片、断线恢复            |
| 运行可恢复 | 任务、事件、审核、产物、checkpoint 必须持久化          |
| 过程可审计 | Agent 每一步操作都需要记录输入、动作、工具结果和验证结果       |
| 质量可评测 | 建立 E2E、Golden Case、LLM 回归、图表回归、性能测试体系 |
| 安全可控  | 文件、Shell、Git、网络、沙箱执行都需要明确权限边界         |

## 4. 目标架构设计

建议将 DevAgent 升级为七层架构：

```text
┌────────────────────────────────────────────┐
│ 1. Frontend Agent Workbench                │
│ 任务台 / 阶段视图 / 图表 / 审核 / 回放       │
└───────────────────┬────────────────────────┘
                    │ REST + WebSocket
┌───────────────────▼────────────────────────┐
│ 2. API Gateway / Realtime Gateway           │
│ Task API / Review API / Event Replay / WS   │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 3. Agent Orchestrator                       │
│ PipelineRunner / ReAct Runtime / Scheduler  │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 4. Agent Runtime                            │
│ Planner / Coder / Tester / Reviewer / Fixer │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 5. Tool Execution Layer                     │
│ File / Shell / Test / Git / Diagram / LSP   │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 6. State + Artifact + Memory Layer          │
│ DB / Vector Store / Artifact Store / Events │
└───────────────────┬────────────────────────┘
                    │
┌───────────────────▼────────────────────────┐
│ 7. Evaluation + Safety Layer                │
│ Validators / Sandbox / Policy / Benchmarks  │
└────────────────────────────────────────────┘
```

该架构的核心变化是：

1. WebSocket 不再作为唯一状态来源，只作为实时增量通道。
2. Agent 动作不再直接信任 LLM 输出，而是经过结构化协议和验证器。
3. 图表不再只依赖浏览器渲染，而是由服务端生成正式 SVG/PNG 产物。
4. 每一次 Agent 执行都可以恢复、回放、审计和评测。

## 5. 第一阶段：稳定 Agent 输出协议

### 5.1 阶段目标

解决 LLM 输出不稳定、工具参数解析脆弱、模型输出格式不一致的问题。

当前部分模型路径依赖文本格式解析，例如：

```text
THOUGHT: ...
ACTION: ...
PARAMS: {...}
```

这种方式在模型输出稍微偏离格式时容易失败。成熟 Agent 平台必须将模型输出统一为结构化协议。

### 5.2 改造步骤

#### 步骤 1：新增结构化输出模块

新增模块：

```text
devagent/agentic/structured_output.py
devagent/agentic/action_schema.py
devagent/agentic/action_validator.py
devagent/agentic/model_adapter.py
```

职责划分：

| 模块                   | 职责                                        |
| -------------------- | ----------------------------------------- |
| structured_output.py | 统一处理模型结构化输出                               |
| action_schema.py     | 定义 Action、ToolCall、AgentDecision 等 Schema |
| action_validator.py  | 校验工具名、参数、路径、安全策略                          |
| model_adapter.py     | 适配 OpenAI、DeepSeek、其他模型能力差异               |

#### 步骤 2：所有工具参数使用 Pydantic 校验

每个工具都需要定义输入 Schema，例如：

```python
class FileEditParams(BaseModel):
    path: str
    old_string: str
    new_string: str
    replace_all: bool = False
```

执行流程改为：

```text
LLM 输出候选动作
    ↓
JSON 解析
    ↓
Pydantic Schema 校验
    ↓
语义校验
    ↓
安全校验
    ↓
执行工具
```

#### 步骤 3：增加自动修复解析机制

当模型输出不合规时，不立即失败，而是进入三段式修复流程：

```text
Parse failed
    ↓
Repair prompt
    ↓
Re-parse
    ↓
仍失败则降级为 ask_user 或 submit failure
```

#### 步骤 4：按模型能力建立 Adapter

不同模型能力不同，不能使用同一套调用假设。

建议定义：

```python
class ModelCapabilities(BaseModel):
    supports_function_calling: bool
    supports_json_mode: bool
    supports_vision: bool
    max_context_tokens: int
    reliable_schema_output: bool
```

根据模型能力选择输出策略：

| 模型能力                  | 使用策略                        |
| --------------------- | --------------------------- |
| 支持原生 function calling | 优先使用原生工具调用                  |
| 支持 JSON mode          | 使用 JSON Schema 输出           |
| 只支持文本                 | 使用严格 prompt + repair parser |
| 不支持多模态                | 禁用 image_read 或降级处理         |

### 5.3 交付物

1. 结构化输出模块。
2. 工具参数 Schema。
3. Action 校验器。
4. Model Adapter。
5. 解析失败自动修复机制。
6. 解析失败测试用例。

### 5.4 验收标准

| 验收项                 | 标准    |
| ------------------- | ----- |
| 工具参数解析成功率           | ≥ 99% |
| 非法工具调用拦截率           | 100%  |
| 无效 JSON 自动修复成功率     | ≥ 90% |
| 所有工具执行前经过 Schema 校验 | 100%  |
| 所有模型路径具备统一 Adapter  | 100%  |

## 6. 第二阶段：Pipeline 产物契约化

### 6.1 阶段目标

解决 Pipeline 阶段产物硬编码、阶段输出缺少强校验、阶段间状态传递松散的问题。

成熟 Agent 流水线必须明确：

1. 每个阶段应该输出什么。
2. 输出文件放在哪里。
3. 输出结构是否合法。
4. 是否通过质量门。
5. 失败后如何重试或回滚。

### 6.2 改造步骤

#### 步骤 1：新增 pipeline.yaml 配置

示例：

```yaml
phases:
  requirements:
    tool: analyze_requirements
    output_dir: 01_requirements
    required_artifacts:
      - path: requirement_specification.md
        type: markdown
      - path: structured_requirements.json
        type: json
    validators:
      - markdown_structure
      - json_schema

  design:
    tool: design_architecture
    output_dir: 02_design
    required_artifacts:
      - path: architecture_design_spec.md
        type: markdown
      - path: design_artifacts.json
        type: json
      - path: diagrams
        type: diagram_collection
    validators:
      - markdown_structure
      - diagram_validation
      - json_schema

  implementation:
    tool: generate_code
    output_dir: 03_implementation
    required_artifacts:
      - path: src
        type: source_tree
      - path: artifact_manifest.json
        type: manifest
    validators:
      - syntax
      - import_check
      - ruff
      - mypy

  testing:
    tool: generate_tests
    output_dir: 04_tests
    required_artifacts:
      - path: tests
        type: test_tree
      - path: pytest_result.json
        type: test_report
    validators:
      - syntax
      - pytest
      - coverage

  delivery:
    tool: generate_report
    output_dir: 06_reports
    required_artifacts:
      - path: executive_report.md
        type: markdown
      - path: final_artifact_manifest.json
        type: manifest
    validators:
      - report_completeness
```

#### 步骤 2：引入 Artifact Contract

每个阶段完成后生成统一产物清单：

```json
{
  "task_id": "xxx",
  "phase": "design",
  "artifacts": [
    {
      "id": "architecture_diagram",
      "path": "02_design/diagrams/architecture.svg",
      "type": "diagram",
      "hash": "sha256:...",
      "status": "valid"
    }
  ],
  "validators": [
    {
      "name": "diagram_validation",
      "status": "passed"
    }
  ]
}
```

#### 步骤 3：阶段输出必须通过 Schema

例如需求阶段必须输出：

```text
functional_requirements
non_functional_requirements
use_cases
constraints
acceptance_criteria
```

设计阶段必须输出：

```text
architecture_overview
components
interfaces
data_model
diagrams
technology_stack
risks
```

测试阶段必须输出：

```text
test_files
coverage_summary
pytest_result
failed_cases
repair_suggestions
```

#### 步骤 4：失败策略标准化

每个阶段支持：

```text
retry
revise
rollback
skip with warning
fail fast
manual intervention
```

例如：

```yaml
retry:
  max_attempts: 2
  on_failure:
    - repair_output
    - rerun_validator
    - ask_user_if_still_failed
```

### 6.3 交付物

1. pipeline.yaml。
2. Artifact Contract。
3. 阶段 Schema。
4. 阶段验证器。
5. 阶段失败处理策略。
6. Pipeline 状态迁移日志。

### 6.4 验收标准

| 验收项               | 标准    |
| ----------------- | ----- |
| 阶段产物 Schema 覆盖率   | 100%  |
| 硬编码 wait_files 移除 | 100%  |
| 阶段输出可验证           | 100%  |
| 阶段失败有明确处理策略       | 100%  |
| Pipeline 执行结果可复现  | ≥ 95% |

## 7. 第三阶段：稳定图表渲染系统

### 7.1 阶段目标

解决图表渲染不稳定、前端和报告产物不一致、Mermaid 语法错误、图表不可复现等问题。

当前策略是：

```text
浏览器 Mermaid
    ↓ 失败
服务端 Kroki
    ↓ 失败
展示源码
```

该策略可以保证页面不空白，但不能保证正式交付质量。成熟系统应将图表渲染升级为服务端确定性产物生成流程。

### 7.2 改造步骤

#### 步骤 1：新增 Diagram IR

不要让 LLM 只输出 Mermaid 源码，而是先输出结构化图表中间表示。

示例：

```json
{
  "id": "system_architecture",
  "type": "component_diagram",
  "title": "系统架构图",
  "description": "展示 API、Agent Core、Tool Layer、Artifact Store 的关系",
  "nodes": [
    {
      "id": "api",
      "label": "API Gateway",
      "kind": "service"
    },
    {
      "id": "core",
      "label": "Agent Core",
      "kind": "runtime"
    }
  ],
  "edges": [
    {
      "from": "api",
      "to": "core",
      "label": "dispatch task"
    }
  ],
  "target_dsl": "mermaid"
}
```

新增模块：

```text
devagent/reporting/diagram_ir.py
devagent/reporting/diagram_compiler.py
devagent/reporting/diagram_validator.py
devagent/reporting/diagram_renderer_service.py
devagent/reporting/diagram_cache.py
```

#### 步骤 2：Diagram IR 编译为 Mermaid / PlantUML / Graphviz

流程：

```text
Diagram IR
    ↓
Compiler
    ↓
Mermaid / PlantUML / Graphviz
    ↓
Syntax Validator
    ↓
Auto Repair
    ↓
Renderer
```

不同图表类型使用不同 DSL：

| 图表类型  | 推荐 DSL                          |
| ----- | ------------------------------- |
| 流程图   | Mermaid flowchart               |
| 时序图   | Mermaid sequenceDiagram         |
| 类图    | PlantUML 或 Mermaid classDiagram |
| 架构图   | Mermaid / Graphviz              |
| 复杂依赖图 | Graphviz                        |
| 状态机   | Mermaid stateDiagram            |
| ER 图  | Mermaid erDiagram               |

#### 步骤 3：服务端固定版本渲染

正式产物必须由服务端渲染，不依赖用户浏览器环境。

建议部署：

```text
Kroki container
Mermaid CLI container
Graphviz
PlantUML
```

渲染服务流程：

```text
diagram_source
    ↓
normalize
    ↓
validate
    ↓
repair if invalid
    ↓
render
    ↓
cache by hash
    ↓
return SVG/PNG URL
```

#### 步骤 4：图表缓存

缓存 Key：

```text
sha256(diagram_source + renderer_type + renderer_version)
```

缓存文件：

```text
artifacts/{task_id}/diagrams/{diagram_id}.svg
artifacts/{task_id}/diagrams/{diagram_id}.png
artifacts/{task_id}/diagrams/{diagram_id}.json
```

#### 步骤 5：图表质量评估

新增 DiagramQualityEvaluator，检查：

1. 语法是否有效。
2. 节点是否过多。
3. 边是否过多。
4. 是否存在孤立节点。
5. 是否存在重复节点。
6. 是否出现乱码。
7. 是否标题缺失。
8. 是否结构不可读。
9. 是否图表类型和内容不匹配。
10. 是否可以导出为正式产物。

### 7.3 交付物

1. Diagram IR。
2. 图表编译器。
3. 图表验证器。
4. 图表自动修复器。
5. 服务端渲染服务。
6. SVG/PNG 缓存。
7. 前端 DiagramViewer。
8. 图表质量评估报告。

### 7.4 验收标准

| 验收项        | 标准    |
| ---------- | ----- |
| 图表一次渲染成功率  | ≥ 95% |
| 自动修复后渲染成功率 | ≥ 99% |
| 正式报告图表一致性  | 100%  |
| 图表 SVG 可下载 | 100%  |
| 图表错误可定位    | 100%  |
| 图表缓存命中可复用  | 100%  |

## 8. 第四阶段：任务状态、事件、审核持久化

### 8.1 阶段目标

解决页面刷新丢状态、审核历史丢失、事件不可回放、任务不可恢复的问题。

成熟 Agent 平台必须将运行状态持久化，WebSocket 只能作为实时增量通道，不能作为唯一状态来源。

### 8.2 改造步骤

#### 步骤 1：设计数据库表

建议使用 PostgreSQL。开发环境可使用 SQLite。

核心表：

```text
tasks
runs
events
approvals
reviews
artifacts
checkpoints
agent_steps
agent_messages
diagram_assets
```

#### 步骤 2：任务表

```sql
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    title TEXT,
    mode TEXT,
    status TEXT,
    current_phase TEXT,
    workspace TEXT,
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    completed_at TIMESTAMP
);
```

#### 步骤 3：事件表

```sql
CREATE TABLE events (
    id TEXT PRIMARY KEY,
    task_id TEXT,
    run_id TEXT,
    event_type TEXT,
    payload JSONB,
    sequence_no BIGINT,
    created_at TIMESTAMP
);
```

#### 步骤 4：审核表

```sql
CREATE TABLE reviews (
    id TEXT PRIMARY KEY,
    task_id TEXT,
    phase TEXT,
    title TEXT,
    summary TEXT,
    quality_score JSONB,
    status TEXT,
    decision TEXT,
    feedback TEXT,
    created_at TIMESTAMP,
    decided_at TIMESTAMP
);
```

#### 步骤 5：产物表

```sql
CREATE TABLE artifacts (
    id TEXT PRIMARY KEY,
    task_id TEXT,
    phase TEXT,
    type TEXT,
    path TEXT,
    hash TEXT,
    metadata JSONB,
    created_at TIMESTAMP
);
```

#### 步骤 6：WebSocket 支持事件补偿

前端连接时携带：

```text
last_event_sequence
```

服务端返回：

```text
last_event_sequence 之后的所有事件
```

这样可以解决：

1. 断线重连。
2. 页面刷新。
3. 多客户端同步。
4. 后续任务回放。

### 8.3 交付物

1. 数据库 Schema。
2. Repository 层。
3. Event Store。
4. Review Store。
5. Artifact Store。
6. Checkpoint Store。
7. WebSocket event replay。
8. 任务恢复 API。

### 8.4 验收标准

| 验收项                 | 标准    |
| ------------------- | ----- |
| 页面刷新后任务状态恢复         | 100%  |
| 审核记录持久化             | 100%  |
| 事件可回放               | 100%  |
| WebSocket 断线重连后补偿事件 | 100%  |
| 任务失败后可查看完整历史        | 100%  |
| checkpoint 可恢复      | ≥ 95% |

## 9. 第五阶段：前端 Agent Workbench 改造

### 9.1 阶段目标

将当前静态 SPA 升级为高质量 Agent 工作台，提升交互稳定性、状态可控性、复杂任务可视化能力。

### 9.2 推荐技术栈

| 能力          | 推荐技术                                  |
| ----------- | ------------------------------------- |
| 前端框架        | React + TypeScript 或 Vue + TypeScript |
| 状态管理        | Zustand / Pinia / Redux Toolkit       |
| 服务端状态       | TanStack Query                        |
| 状态机         | XState                                |
| 代码查看        | Monaco Editor                         |
| Markdown 渲染 | markdown-it / remark                  |
| 图表展示        | 自研 DiagramViewer                      |
| 日志列表        | Virtualized List                      |
| 表单校验        | Zod                                   |
| 构建工具        | Vite                                  |
| 测试          | Vitest + Playwright                   |

### 9.3 交互状态机

任务状态建议标准化为：

```text
idle
creating_task
running
waiting_review
waiting_user_input
paused
repairing
completed
failed
aborted
```

每个状态要明确：

| 状态                 | 用户可操作              |
| ------------------ | ------------------ |
| running            | 暂停、中止、查看日志、查看已生成产物 |
| waiting_review     | 通过、要求修改、拒绝、添加反馈    |
| waiting_user_input | 回复问题、补充上下文         |
| paused             | 恢复、中止              |

## 16. 总结

DevAgent 当前已经具备完整的软件工程 Agent 基础能力，但要成为成熟 Agent 平台，需要从“功能堆叠”转向“工程稳定性建设”。

最关键的改造顺序是：

```text
结构化输出
    ↓
Pipeline 产物契约
    ↓
状态持久化
    ↓
服务端图表渲染
    ↓
前端 Agent Workbench
    ↓
执行账本与回放
    ↓
评测、安全和长期记忆
```

其中，前三项是基础稳定性，第四项解决图表交付质量，第五项解决用户交互体验，后两项决定平台是否可以长期演进。

本方案建议优先完成 P0 项，确保 Agent 执行稳定、图表稳定、状态可恢复，再逐步推进前端体验、评测体系、多 Agent 协作和长期记忆能力。
